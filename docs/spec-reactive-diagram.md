# spec — 連動する図 (#1161)

図の中の要素が互いに関連して動く形を、 記法で書けるようにする。 実装着手前の SSOT。

## 0. なぜ

dragon の看板は `animated diagram dsl`。 実測すると catalog 422 件のうち **65% が静止画**で、
**要素が連動して動く図は 6% (27 件)** しかない。

さらに、 その 27 件も連動していない。 良い例とされる `richPipelineDemo` を分解すると、

- 5 つの水位は **段が 5 つの値を手で書いている**。 値どうしに関係が無い
- 工程の連なりは `edge` の見た目だけ。 `s1` が 100 になっても `s2` は影響を受けない
- 補間 24 回は「4 つの値 × 段ごとの手書き」 で、 要素が増えるほど書く量が増える

**関係を書く場所が無い**のが根本。 だから全部を段が肩代わりしている。

## 1. 前提事実 (実測)

| 事実 | 出どころ |
|---|---|
| 動く部品 (`dyn-*`) 5 種は `{signal}` を読む | `kinds/dyn-shape.tsx` に 28 箇所 |
| 図表 10 種 (`chart-*` / `funnel` 等) も状態を読む | `kinds/chart-bar.tsx` 他が `stateValues` を `resolveChartData` に渡す |
| 記法の top-level は 9 種 (`title` / `type` / `actors` / `flow` / `states` / `animation` / `viewport` / `lanes` / `groups`) | `v05/parser.ts` |
| `states` は初期値のみを持ち、 値どうしの関係を書けない | 同上 |
| 段 (`animation.step`) だけが値を動かせる | `compile.ts` |

## 2. 決めたこと

### 2.1 「起点」 という分類を作らない

当初 パーツを 源 / 管 / 面 の 3 つに分ける案を検討したが、 **起点かどうかは要素の性質ではなく
その場の配線で決まる**。 段が動かせば起点、 前の値が動かせば中間になる。 同じものが文脈で
呼び名を変えるなら、 種類として持つべきではない。

分類は 2 つ。

| 分類 | 役割 |
|---|---|
| **値** | 動くもの。 トリガーか式で動く |
| **面** | 値を読んで描くもの (水位 / 棒 / 輪 / 図表) |

### 2.2 3 層に分ける

| 層 | 何を決めるか | 記法 |
|---|---|---|
| **配置** | 何を / どこに / どの値を読むか | `actors` / `flow` |
| **依存** | 値どうしの関係。 **時間を持たない** | `values` (新設) |
| **動き** | いつ何を動かすか | `animation` |

分ける理由は、 混ぜると片方を変えるたびに両方を書き直すため。 いまは `animation` が依存も
肩代わりしているので、 順序を変えると全部の値を書き直すことになる。

### 2.3 値が動く 3 通り

```
values:
  v.done:   { trigger: step "ingest", to: 100, dur: 2s }   # 段が引く
  c.done:   { trigger: v.done >= 100, to: 100, dur: 2s }   # 前の値が引く
  p.done:   "{c.done} - 3"                                  # 常に追随 (式)
```

| 書き方 | いつ動くか | 時間を持つか |
|---|---|---|
| `trigger: step ...` | その段が始まったら | 持つ |
| `trigger: <条件>` | 条件が成り立った瞬間 | 持つ |
| `"{式}"` | 常に | 持たない |

**式とトリガーは別物**。 式は「常に成り立つ関係」、 トリガーは「成り立った瞬間の出来事」。

### 2.4 これで「フロー 1 が終わったらフロー 2」 が書ける

段が引くのは最初の 1 つだけで、 あとは連鎖する。 工程を 1 つ挟むのも `values` に 1 行。

### 2.5 名前は英語、 `as` で別名

既存の top-level が英語 (`title` / `actors` / `flow` / `animation`) なので揃える。 中身の文字列
(表示名) は日本語でよい。

```
actors:
  - 検証 as v: { shape: wave, col: 1, reads: v.done }
```

表示名と参照名を分けるので、 **表示を変えても参照が壊れない**。 いまは名前がそのまま id に
なるため、 表示を直すと `flow` の矢印も全部直す必要がある。

点付きの名前 (`v.done`) は要素ごとに値をまとめるための書き方。 強制しない (`vDone` でも動く)。

## 3. 記法の全体像

例を 2 つに分ける。 **段 1 まで入った今の記法で書ける形**と、**段 2-3 の後に書ける形**。

分ける理由は、片方を検査に載せるため。 前者は `textDslToDiagram` と CDL の `compile` に通して
図へ組み立てられることを
`packages/dragon/test/spec-buildable-example.test.ts` が確かめる。 後者は未実装の計画なので
組み立てられないのが正しく、検査対象にしない。

分けていなかった間、この節の例は **25 件の error** を出す状態だった (#1207 で実測)。
そのうち `type: pipeline` と点付きの値名は段 2-3 が入っても解けるようにならない誤りで、
計画部分に紛れて気付けなかった。

### 3.1 今書ける形 (段 1 まで)

```
title: "取込みの流れ"
type: flow

# --- 配置 ---
actors:
  - 検証 as v: { kind: process, value: "{vdone}" }
  - 変換 as c: { kind: process, value: "{cdone}" }
  - 加工 as p: { kind: process, value: "{pdone}" }
  - 保存 as s: { kind: process, value: "{sdone}" }
  - 全体:      { kind: process, value: "{progress}" }

flow:
  - v -> c: "変換"
  - c -> p: "加工"
  - p -> s: "確定"

# --- 初期値 ---
states:
  vdone: 0
  cdone: 0
  pdone: 0
  sdone: 0

# --- 依存 ---
values:
  progress: "({vdone} + {cdone} + {pdone} + {sdone}) / 4"
```

段は 1 つ。 要素を 1 つ足す時に触るのは `actors` と `states` と `values` に 1 行ずつ。

**この例は `flow:` を名札としてしか読まない**。 `type: flow` は箱を書いた順に鎖状に繋ぎ、
`flow:` の from / to はそのまま矢印にならない (#1269 でこの形を知らせるようにした)。
書いた端どおりに繋ぐには、動き (`animation:`) / 向き (`direction:`) / 箱の縦列 (`lane:`) の
どれかを書く (#2374 で 3 つとも知らせの案内に出るようにした)。

この例は 3 つとも書いていないので鎖になる。 上の並び (`v` → `c` → `p` → `s` → 全体) と
`flow:` の 3 行が同じ順なので、出来る図は書いたとおりに見える。
段を足す時は `animation:` を書けば `flow:` の端がそのまま矢印になる。

**以前の記述は実測と逆だった** (#2374)。 「`animation:` を足すと書いた矢印が消える」 と
書いていたが、実測では動きを足すと書いた端どおりに繋がる。 `#1209` は別の不具合
(別名と動きの併記で矢印の指す箱が消える) で、既に閉じている。

この形で書けないのは工程の連なり。 `vdone` が 100 になっても `cdone` は動かないため、
5 つの値を段が手で書くことになる (§ 0 で挙げた `richPipelineDemo` と同じ形)。
それを解くのが段 2。

### 3.2 段 2-3 の後に書ける形 (未実装)

```text
type: pipeline

# --- 配置 ---
actors:
  - 検証 as v: { shape: wave, col: 1, reads: v.done }
  - 変換 as c: { shape: wave, col: 1, reads: c.done }
  - 加工 as p: { shape: wave, col: 2, reads: p.done }
  - 保存 as s: { shape: wave, col: 3, reads: s.done }
  - 全体:      { shape: ring, col: 3, reads: progress }

flow:
  - v -> c: "変換"
  - c -> p: "加工"
  - p -> s: "確定"

# --- 依存 ---
values:
  v.done:   { trigger: step "取込み", to: 100, dur: 2s }
  c.done:   { trigger: v.done >= 100, to: 100, dur: 2s }
  p.done:   { trigger: c.done >= 100, to: 100, dur: 2s }
  s.done:   { trigger: p.done >= 100, to: 100, dur: 2s }
  progress: "({v.done} + {c.done} + {p.done} + {s.done}) / 4"

# --- 動き ---
animation:
  - step: "取込み" 8.0s
```

段 2 (`trigger` / `to` / `dur`) は入った。 残るのは段 3 の `reads` と `type: pipeline`、 それに
点付きの値名 (`v.done`) で、この例が組み立てられないのはその 3 つのため。

**点付きの値名は採らない**と決めた (#1161 段 2)。 描画側が箱の文字の `{名前}` を置き換える時に
見る範囲が英数字と `_` だけで、点を含む名前は置き換えられずに生の形が出る。 記法だけで点を
許すと「書けるのに届かない」 名前ができる。 まとめ方が要る時は `vDone` のように書く。

置き換えの範囲そのものを広げる話は `#1189` (英数字でない actor 名で見本の値が届かない) と同じ
層で、そちらで決める。

**`title:` を書いていないのは検査対象から外す印**。 検査は `title:` で始まる block だけを
parser に通すため、計画の例が誤って落とされない。

### 3.3 段 2 で入った書き方

きっかけは 2 通りある。 どちらも `to` (動いた先) と `dur` (動く長さ) を伴う。

| 書き方 | いつ動き出すか |
|---|---|
| `trigger: step "取込み"` | その段が始まった時 |
| `trigger: vDone >= 100` | 別の値が境目を通った時 |

```text
title: "連鎖"
type: flow

actors:
  - 検証
  - 変換

states:
  vDone: 0
  cDone: 0

values:
  vDone: { trigger: step "取込み", to: 100, dur: 2s }
  cDone: { trigger: vDone >= 100, to: 100, dur: 2s }

animation:
  - step: "取込み" 4s
```

動き始めの値は `states:` から取る。 きっかけ形では両方書くのが正しい形なので、名前が重なっても
知らせは出さない (式形は従来どおり知らせる)。

#### 段は割らずに時計で解く

描画側の動きの模型は段と、段の中の線形補間しか持たない。 条件で動き出す仕組みも、値ごとの
長さも無い。 そこで組み立ての時点で段に時計を 1 本引き (`0` から段の長さまでの補間)、各値を
「時計を読む傾斜」 として書く。

```
値 = from + (to - from) * min(max((時計 - 開始) / 長さ, 0), 1)
```

段を割らないのは、段が見出し / 本文 / 印を持つ表示物だから。 割ると段送りの見え方と件数が
変わる。

連鎖の時刻は逆算で決まる。 相手も段の中で線形に動くため、境目を通る時刻が求まる。

#### 畳めない形

4 つある。 いずれも図に載せず、書いた行で伝える (`value-trigger-unresolved`)。

| 形 | 伝えること |
|---|---|
| 段の名前が無い | その名前の段を書くか、段の名前に合わせる |
| 相手が動く値でない | 見張る相手も `trigger:` を持つ値にする |
| 相手が境目を通らない | 相手が通る値を境目にするか `to` を見直す |
| 段に収まらない (開始 + 長さ > 段の長さ) | 段を長くするか `dur` を短くする |

きっかけが一周している形も同じ扱いで、どれか 1 つを `trigger: step ...` に変える。

## 4. 決めた論点

### 4.1 式に書けるもの

四則 (`+` `-` `*` `/`) と括弧、 比較 (`>` `>=` `<` `<=` `==` `!=`)、 `min` / `max` の 2 つだけ。

関数呼び出しは入れない。 入れると「どの関数があるか」 を覚える必要が出て、 記法が言語になる。
四則で足りない形が出てから足す。

比較の結果は真偽で、 数として使う時は真 = 1 / 偽 = 0。 色や表示の切替に配れる。

### 4.2 輪の扱い

**その値だけ止め、 残りは動かす**。 図全体を止めない。

1 箇所の輪で図が消えると、 どこが悪いか分からなくなる。 輪に入った値は初期値のまま置き、
それを読む要素にだけ知らせる (`onNotice`)。

検出は依存を辿って自分に戻るかを見る。 段 1 の実装時に入れる (後付けにすると、 輪を含む図が
既に存在する状態で入れることになり、 既存の図が壊れる)。

### 4.3 計算の順序

**参照の関係から解く**。 書いた順に依存しない。

```
values:
  progress: "{done} / 100"    # 先に書いてよい
  done:     "{a} + {b}"
```

書いた順にすると、 行を並べ替えただけで壊れる。 依存を辿って順序を決める (`a` / `b` → `done`
→ `progress`)。

### 4.4 図表 10 種が値を読む形

読めるようにする。 `chartData` の各値が `{signal}` を受ける。

```
- 流入: { shape: bar, reads: [{検索}, {SNS}, {直接}] }
```

**cdl 側で実装済み**。 `chart-bar` / `chart-pie` / `chart-line` / `funnel` / `mind-map` が
`stateValues` を受け取り、 `resolveChartData` / `resolveMindData` に渡している。

この節を書いた時点では配列を受け取って一度描くだけで、 状態を読む経路が無かった。

### 4.5 既存の `states` との関係

**両方書ける**。 役割が違う。

| 項目 | 役割 |
|---|---|
| `states` | 初期値 (`counter: 0`) |
| `values` | 関係 (`waiting: "{inflow} - {done}"`) またはきっかけから動く値 |

式形と同じ名前が両方に出たら **`values` を優先**し、食い違いを伝える。きっかけ形では
`states` 側を動き始めの値として使うため、同じ名前を両方に書くのが正しく、知らせは出さない。

既存の図は `states` だけを持つので、 挙動は変わらない。

## 5. 反例

- 値を 1 つも書かない図 → 静止する (いまと同じ)
- `values` に輪がある → その値だけ止め、 残りは動く
- トリガーの条件が一度も成り立たない → その値は図に載せず、書いた行で伝える
- 段が無くきっかけ形の `values` だけ → その値は図に載せず、段が無いことを伝える
- 同じ値に `trigger` と式の両方 → 記法として受け付けない
- 式形の `values` と `states` に同じ名前 → `values` を優先し、食い違いを伝える (§ 4.5)
- きっかけ形の `values` と `states` に同じ名前 → `states` を動き始めの値として使う (§ 3.3)

## 6. 破れる条件

- 値が数百になると、 毎 frame の計算が図の描画より重くなる。 上限を決める必要がある
- トリガーの条件が同時に成り立つと、 動く順序が決まらない。 宣言順で決めるか、 同時に動かすか
- 比較の結果を数として使う形 (§ 4.1) は、 真 = 1 の前提が変わると全ての図が壊れる

## 7. 実装しない

- 関数呼び出し / 条件分岐の式 (`if`)。 まず四則と比較で足りるかを見る
- 値の履歴 (前の frame の値を参照する)。 循環の温床になる
- 外部からの値の注入 (API / file)。 別の話
