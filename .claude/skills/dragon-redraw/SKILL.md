# dragon-redraw — 描き方を作り直す

## 位置付け

図が読みにくい時、原因は 3 つの層のどれかにある。

| 層 | 例 | 直す場所 |
|---|---|---|
| 例文 | 名前が長すぎる / 値が不自然 | `apps/playground-spa/src/topics/catalog/*.cdl.ts` |
| 記法 | 書きたいことを書く欄が無い | `packages/dragon/src/compile/` |
| 描画 | 枠が中身に合っていない / 線の太さが一様 / 箱が要らない所に出る | engine の描画 |

本 skill が相手にするのは 3 つ目だけ。
例文を直しても記法を足しても、描き方が同じなら見え方は変わらない。

層を取り違えると、直したのに良くならないという結果になる。
2026-09-29 に 3 つの図で実際にそうなった。
例文の文言を整える案を出した後、user から「そもそものクオリティが低いと言ってるんだけど」 と差し戻された。

## 起動 trigger

user 明示起動のみ。

```
/dragon-redraw 図を速くする
/dragon-redraw          引数なしなら測って候補を出す
```

引数は catalog の図の id (画面の `data-item-id`、日本語の題)。

## 前提

- 起動 dir は dragon repo root
- 見本帳の dev server が動いている (`pnpm --filter dragon-playground-spa dev`、4323 番)
- 作業 branch に居る (既定 branch では書けない)

## 段取り

6 段ある。
順に通す。
飛ばしてよいのは 5 段目より前が済んでいる再開時だけ。

### 1. 測る

```bash
node apps/playground-spa/scripts/drawing-measure.mjs --group charts --samples 14 --interval 400
```

3 つの数を、群ごとに広がりの低い順で並べる。

| 数 | 何を映すか |
|---|---|
| 文字の広がり | 図が枠を使い切っているか |
| 切れた名前 | 末尾が `…` で終わる名前の数 |
| 読める字 | 省略の印と空白を除いた字の数 |

図形ではなく文字を測るのは、どの図も枠いっぱいにカードの地を敷くため。
`node-body` の矩形が 1 つで枠の 65% を占めるので、図形を数えると全図が 9 割で並んで差が消える。

**広がり 1 つで判定しない**。
広がりは一番外側の文字で決まるため、内側の名前が読めるようになっても動かない。
描き方を 3 件直した回は、3 枚のうち 2 枚で広がりが 1 ポイントも動かず、残る 1 枚も
1 ポイントしか動かなかった。 同じ 3 枚で切れた名前は 5 件 → 3 件 と 1 件 → 0 件 に
減っている (#2669 で実測)。

広がりで相手を探し、切れた名前と読める字で直ったかを見る。

出た数は artifact と決定の記録に 3 つとも書く。
直す前の値を残さないと、直った後に「上がった」 と言えない。

引数なしで起動した時はこの段の出力が候補一覧になる。
どれを相手にするかは user が決める。

### 2. 今の絵を出す

```bash
node apps/playground-spa/scripts/design-export.mjs <図の id>
```

段ごとの SVG と色変数が `.context/design/<図>/` に出る。

線を引く動きは JS が駆動するので、`renderToStaticMarkup` では起点しか出ない。
画面から取るこの経路だけが、引き終わった絵を持つ。

### 3. 狙いを手で描く

同じ `viewBox` で、狙う絵を SVG として手で書く。
置き場は `.context/redraw/<図>/target.svg`。

守ることが 3 つある。

第一に、枠を今と同じにする。
枠が違うと、良くなったのか大きくしただけなのかが読めない。

第二に、色は見本帳の色変数から取る。
`--d-accent` や `--d-text-secondary` のような名前で引き、16 進の値を手で決めない。
全体の意匠を崩さないための唯一の経路がこれになる。

第三に、engine がまだできないことを絵の中に書き込む。
「この位置決めは実装が無い」 を絵に書いておかないと、user は実装済の提案だと読む。

### 4. 見せて決めてもらう

artifact を必ず作る。
今の絵と狙いの絵を並べ、決めてほしいことを 3 から 4 件だけ載せる。

載せる項目は 4 つ。

| 何を | 中身 |
|---|---|
| 測った数 | 直す前の 3 つの数 (文字の広がり / 切れた名前 / 読める字) |
| 今の絵 | 段ごとに全部。 1 段だけ見せて済ませない |
| 狙いの絵 | 同じ枠で並べる |
| 決めてほしいこと | 3 から 4 件。 各件に推す案を 1 つ明示する |

`artifact-design` skill の頁の契約に従う。
色は変数として `:root` に置き、明暗の両方を書く。

### 5. 直す

決まった案を engine に実装する。

直す先は `packages/dragon/src/` の描画側。
`@cardenelabs/cdl` は別の package なので、この repo からは中を直せない。
cdl の側でしか直せない項目が出たら、そこで止めずに別 Issue に切り出して残りを進める。

実装したら段取り 1 をもう一度走らせ、数が上がったことを確かめる。
上がらなかったら実装が狙いに届いていない。

### 6. 崩れを確かめる

```bash
pnpm build:packages && pnpm verify
```

描画を変えると、焼き付けた見た目を見る検査と 2 つの記法の一致を見る検査が動く。
落ちた検査が狙った変更を映しているのか、巻き込み事故なのかを分ける。

狙った変更なら焼き付けを取り直す。
巻き込み事故なら実装を直す。

## 決めたことを残す

決まった内容を `docs/design/drawing/<図種>.md` に書く。

書く欄は 4 つ。

| 欄 | 中身 |
|---|---|
| 測った数 | 3 つの数を直す前と後で |
| 決めたこと | 何をどう描くか |
| 退けた案 | 出したが選ばなかった案と、その理由 |
| まだできないこと | 実装していない項目と、その行き先 (Issue 番号) |

退けた案を書くのは、次に同じ議論をやり直さないため。

隣の `docs/design/notation/` とは軸が違う。
あちらは図 1 つの見た目を焼き付けて残す場所で、こちらは描き方の判断を残す場所になる。

## 責務境界

### 完成形の定義

以下がすべて揃った時に完了とする。

- 直す前と後の文字の広がりが数で出ている
- 今の絵が段ごとに `.context/design/<図>/` にある
- 狙いの絵が同じ枠で `.context/redraw/<図>/target.svg` にある
- artifact が公開され、決めてほしいことに user が答えている
- 決定が `docs/design/drawing/<図種>.md` にある
- `pnpm verify` が通っている

### 統合先 skill

| 関係 | skill | 何を渡すか |
|---|---|---|
| 上流 | `/dragon-review` | 採点で低かった図を本 skill に渡す |
| 下流 | `/dragon-design` | 描き方が固まった図の見た目を意匠帳に納める |
| 併用 | `artifact-design` | 段取り 4 の頁の契約 |
| 併用 | `/verify` | 段取り 6 |

### 責務外

- 記法を足すこと (`shape:` や `axes:` のような欄の追加) は別の Issue で扱う
- 例文の題材を決めること (何を描くかの考案) は `/dragon-diagram` が持つ
- 図 1 つの配色を決めることは `/dragon-design` が持つ
- `@cardenelabs/cdl` の中を直すこと (別 package のため本 repo から触れない)

## 落とし穴

- 文字の広がりが低いこと自体は欠陥ではない。 計器の図は数字 1 つしか置かないので 1% になる。 数は相手を探す入口で、判定そのものではない
- 広がりが動かなかったことを「直っていない」 と読まない。 広がりは外周で決まるので、内側の名前が読めるようになっても動かない。 直ったかは切れた名前と読める字で見る
- 測れなかった図を 0% として扱わない。 script は測れた件数と測れなかった理由を別に出す
- `renderToStaticMarkup` で絵を作らない。 `draw:` の動きは JS が駆動するので、起点しか出ない
- 画面から取った SVG は `width: 872px !important` を持つ。 artifact に貼る前に大きさの宣言を外す
- 枠を変える提案をする時は、変えた後の数を必ず添える。 枠を小さくすれば割合は上がるので、数だけでは良くなったか判らない
