## API overview (excerpts)

This page only shows the overall API landscape.
Each API's arguments, return values, and examples are consolidated in [API Reference](/docs/en/cdl/reference/api).

### Low-level builder

This is the primitive API that starts from `diagram()`.
It corresponds to mermaid's free-form notation and lets you assemble lanes, nodes, edges, and phases one at a time.

```ts
diagram(id, { topic })
  .lane(id, opts)
  .node(id, opts) / .nodes([...])
  .edge(from, to, opts) / .edges([...])
  .state(id, opts)
  .phase(id, opts, build)
  .build()
```

Call `.build()` to return an immutable `CdlDiagram`.
Use this low-level API directly when you need fine-grained layout control.

### High-level 6 presets

These APIs offer mermaid-equivalent ergonomics with a single function plus chain.
You get six variants: sequence, flow, swimlane, topology, er, and stateMachine.

```ts
swimlane({ lanes: [...] })
flow({ ... })
sequence({ actors: [...] })
topology({ ... }).group(...).add(...).connect(...)
er({ ... }).entity(...).relation(...)
stateMachine({ ... }).state(...).transition(...)
```

Every preset compiles internally to the low-level builder.
For preset selection guidance, see the [high-level API table in the API Reference](/docs/en/cdl/reference/api).

### Verifier

These functions invoke cdl's unique "eye" — the mechanism that matches author intent against the rendered screen.
You get three routes (`validate` / `verifyDiagramDom` / `verifyAuthorIntent`) with different verification granularities.

```ts
validate(diagram)
visualValidate(diagram) / visualValidateAll(diagrams)
verifyDiagramDom(page, diagram) / verifyAllDiagramsDom(page, diagrams)
verifyAuthorIntent(page, diagram) / verifyAuthorIntentAll(page, diagrams)
```

For function signature details see the [API Reference](/docs/en/cdl/reference/api).
For the role split among the three routes, see the [Verifier Guide](/docs/en/cdl/reference/verifier-guide).

## Overview of the "eye"

cdl ships a mechanism that no other diagram tool provides: **the engine automatically verifies that author intent matches the actual rendered screen**.
Three commands let you step from static validation to live-screen verification.

```bash
pnpm validate:diagrams      # static layout collision detection
pnpm verify:dom             # render DOM consistency (engine self-consistency)
pnpm verify:intent          # author intent vs. live screen (the mermaid essence)
```

You run these commands with a dev server up.
The role split, tolerance design, and real code examples are collected in the [Verifier Guide](/docs/en/cdl/reference/verifier-guide).
